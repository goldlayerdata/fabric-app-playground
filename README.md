# Fabric app playground

**Learn to read and build a Fabric app the way you learned to read a Power BI project.**

[Open the playground →](https://goldlayerdata.github.io/fabric-app-playground/) · [Visuals →](https://goldlayerdata.github.io/fabric-app-playground/visuals/) · Free, in your browser, nothing to install

## Why this exists

If you've saved a report as a **Power BI project (PBIP)**, you've seen the idea: the report and the semantic model become **folders of plain text files** that you can open, read, compare and keep in Git ([Power BI Desktop projects](https://learn.microsoft.com/power-bi/developer/projects/projects-overview)).

**A Fabric app is a folder of text files too**, but nobody generates it for you from a canvas. The pages are code (TypeScript and React), and the links to your Fabric data are small config files. You, or an AI agent, write them, and someone has to be able to read them.

This playground teaches Power BI developers to do exactly that, one step at a time, from an empty folder to an app with report pages, a lakehouse, its own data and permissions. Each idea starts in Power BI terms. A companion page, **Visuals**, puts 21 Power BI visuals beside the code each one takes in an app.

## The files, in Power BI terms

These are the files the lessons create, with the closest thing in a PBIP project. They're comparisons to help you find your feet, not exact equivalents.

| In the Fabric app folder | What it is | Closest thing in a PBIP project |
| --- | --- | --- |
| `package.json` | The app's name, the packages it uses and its commands (`npm run dev`) | The `.pbip` file at the root, which points at the report to open |
| `rayfin/rayfin.yml` | The app's settings: which Fabric items it connects to, and how each one signs in | `definition.pbir`, pointing the report at its semantic model |
| `rayfin/connectors/<name>/schema.ts` | Generated by the CLI: what each connection can do (for a semantic model, run a DAX query). Not edited by hand | Files Power BI Desktop writes for you |
| `src/services/rayfinClient.ts` | The one place the connections are wired into the app | The report's connection to its model |
| `src/App.tsx`, `src/SalesOverview.tsx`, `src/components.tsx` | The pages and the visuals on them, written as code | The `.Report` folder's pages and visuals (`page.json`, `visual.json`), but written by you, not by Desktop |
| `src/data.ts` | The DAX queries the pages send, and the code that reads the results | The queries a visual sends for you (what Performance analyzer shows) |
| `rayfin/data/SalesTarget.ts` | A table the app keeps itself, with who may read and change it | No real match: a small database the app owns. The "who may" part is a bit like a role in the model |
| `.gitignore`, Git | What stays out of source control, and the history | The same idea as a PBIP's `.gitignore` |

The cheat sheet [Fabric apps: can you read what the AI wrote?](https://goldlayerdata.com/post.html?slug=fabric-apps-can-you-read-what-the-ai-wrote) shows the folder of a new Fabric app on one page.

## The lessons, and what is simulated

A Gold Layer playground where Power BI developers build a Fabric app from an empty folder, chapter by chapter. Chapter 1: create the project, add a semantic model connector, wire the client, then build a report-style 16:9 page in TypeScript and React, make it interactive, and review a page "an agent" wrote. Chapter 2: add a second semantic model, register it in the client, and ask both models from one page. Chapter 3: read a lakehouse through an entity connector, and keep totals in the model. Chapter 4: give the app a database of its own and read and write sales targets. Chapter 5: sign-in, claims and permissions: who sees and changes which targets. A second page, **Visuals** (`visuals/`), shows each Power BI visual beside the same visual running in a Fabric app, with what it takes. Unofficial, and not affiliated with Microsoft.

There is no Fabric and no model behind it:

- **The terminal** simulates the Rayfin 2.0 commands the lessons use (`npm create @microsoft/rayfin@latest … --template dataapp`, `npm install`, `npx rayfin connector add`, `connector invoke`, `connector search`, `connector inspect`, `npm run dev`, `npx rayfin up`, `npx rayfin up connector apply`). What they write (`package.json`, `rayfin/rayfin.yml`, the connector's `schema.ts`) follows the Rayfin docs and the data app template as installed by the Rayfin CLI 2.0.0. Lines we could not check against the real output start with `Playground:`. Sign-in is skipped.
- **The lakehouse** (Chapter 3) is simulated too. `connector add --type fabric-sqlanalytics` writes what the Rayfin CLI 2.0.0 writes (its placeholder `schema.ts` and messages are taken from its code); `metadata.json` has the documented shape, with the playground's own types and values. Reads (`select`, `where`, `orderBy`, `first`, `after`, `execute`, `executePaginated`) are answered in the browser from `data/lakehouse.json`, one page of 100 rows unless `first` says otherwise, as rayfin.ai describes; cursors are made up. The Log's "runs as" line comes from each connector's `auth` in `rayfin.yml`.
- **The app's own database** (Chapters 4 and 5) is simulated in the browser (`src/app-data.mjs`). `npx rayfin up db apply` reads the entities in `rayfin/data/` (a small parser of their decorators; the real CLI collects every exported entity class), compares them with what it applied last, and stops before the changes Rayfin's docs call potentially destructive unless `--force` is given; a `@text()` without `max` applies, then the data API answers "Internal server error", as the docs describe. The page's `rayfinClient.data` calls are checked against the entity's permission rules (`policy` with `.eq`, `.neq`, `.and`, `.or`; `include`, `exclude`) for the claims of the person on the **Signed in as** switch (made-up people), and rows are kept with the project in this browser. With dynamic claims on, the project's `udf.authClaims` function runs in the preview's sandbox at each switch. The **Data** tab appears once the data service is on; it shows every row, ignoring permissions (no real app has that view), and can send a request directly. The real CLI's output and the data API's refusals aren't documented word for word: those lines start with `Playground:`. `rayfin init` is not rerun (what it writes in a data app project isn't documented); the lesson turns the service on by hand, as Microsoft Learn describes.
- **The Rayfin packages** are simulated. The editor checks the learner's code against their real 2.0 signatures (a subset, MIT: `src/editor-types/packages/`), and only once the project has "installed" them. In the page, `executeQuery` matches the connector and the query text against saved results from that connector's model (two Contoso models: `contoso` and `pareto`) and returns them in the connector's result shape. Connector names resolve as in Rayfin 2.0 (`src/connectors-sim.mjs`): any case finds a connector, but its runtime is looked up by the exact configured name, and a semantic model connector without one hands the page the raw payload (placeholder bytes here), with no error.

## Run it

```powershell
npm ci
npm run dev        # http://127.0.0.1:5180 (Visuals: /visuals/), rebuilds on save
npm run build      # static site in dist/
npm run preview    # serves dist/ at http://127.0.0.1:5181
npm run check      # checks the lessons, builds them from an empty folder step by step, then checks the Visuals page
```

You need Node.js 22. The local servers listen on 127.0.0.1 only. `dist/` is a plain static site (GitHub Pages works). Everything is bundled from pinned packages; nothing loads from a CDN.

**Where the numbers come from, and how they are checked.** The page reads the playground's saved answers (`data/snapshots.json`, `data/catalog.json`). Each `.dax` file must send exactly the text a saved answer was captured with: the build and `npm run check` stop if not. A few answers are derived, and the page says so under Where the numbers come from: the slicer's answer for two or three years is the sum of the saved per-year answers, and revenue by category and year is the per-year answers stacked. `data/visuals-extra-answers.json` takes answers captured for this page only (none yet); each must be the exact text of one of the `.dax` files. `tools/check-visuals.mjs`, part of `npm run check`, also checks that every query the app code can send has an answer, that every number the page's text quotes from the data (such as a tooltip's "$60,466,772") is in a saved answer, so a new snapshot can't leave an old number on the page, that `pages.mjs` and the pages agree and its lesson links name real lessons, and that the page's code type-checks. Line counts are worked out from the code at run time, so they can't go stale.

## Data

`data/catalog.json` lists every query the simulated semantic model connectors can answer, each with its `connector` (150). For `contoso`, the Contoso measures model in [gold-layer-examples](https://github.com/goldlayerdata/gold-layer-examples) (`examples/default_measures/gold-layer-data-contoso-measures.pbip`): basics, totals and categories for every year and store country, the "Measure or query" queries, and saved errors. For `pareto`, the Pareto model (`examples/pareto/gold-layer-data-pareto.pbip`: the same tables and data, with Pareto measures): categories with their running share and the headline for every year, the cutoff picks, and `[Revenue]` from both models, with where each model keeps it. `data/snapshots.json` holds their results. The queries use each model's own measures (`[Revenue]`, `[# Orders]`, `[Revenue Cumulative %]`, `[Cutoff Headline]`…), the way a real app's queries do.

To retake the snapshots, open both PBIPs in Power BI Desktop, each in its own window, then:

```powershell
npm run catalog                                                # tools/make-catalog.mjs -> data/catalog.json
npm run snapshots -- -ContosoPort <port> -ParetoPort <port>    # tools/snapshot.ps1: runs each query over ADOMD against its model
```

`data/lakehouse.json` is the lakehouse of Chapter 3: its `metadata.json` (two tables, `sales` and `store`), every store, and the 283 sales lines of the stores in France in 2023, from `datasets/contoso` in gold-layer-examples (prices rounded to 4 decimals, as the model stores them). Those lines add up to the model's `[Revenue]` for France in 2023, which `npm run check` verifies against the saved snapshot.

Queries match on the connector and the text, ignoring spacing and letter case: `EVALUATE ROW ( "Revenue", [Revenue] )` has one answer from each model. `npm run check` finds every query the project can send (query functions are called with every year and store country, and the runner each one goes through names its connector) and fails if one has no saved answer.

## The lessons

One app, built from an empty folder. Structured the way Microsoft Learn builds training (modules of short units, a knowledge check at the end of a module, summaries) and the way the Rayfin docs teach (numbered steps, then what to read next). Only the structure is borrowed.

Chapters group the modules (`chapters` in `src/course.mjs`), and parts group the chapters (`parts`): Read your data (first steps), Store and protect data (building on it), Extend and ship (going further). Every chapter is in exactly one part, in order; `npm run check` verifies it. Lessons are numbered within their chapter: Chapter 4's lessons are 4.1, 4.2 and so on. Modules have no number on screen; they are plain headings. A chapter added at the end moves no number; one put between others moves the numbers after it. Links and progress are kept by lesson and module id, so a number that moves breaks nothing. Chapters not built yet are listed as Coming soon, with their planned lesson titles. The start screen shows each chapter's state (done, in progress, not started, coming soon); its main button follows the chapter picked, and starting a chapter not started yet builds the project as that chapter begins and clears the terminal, with Undo.

Lesson numbers come from positions in `src/course.mjs` and are never written anywhere else: lesson text refers to lessons and chapters by title, and `npm run check` fails on "lesson 4", "chapter 2" or "4.2 Model a sales target"-style references.

Each lesson is the same set of cards: the idea in Power BI terms with "You'll be able to" and "Builds on", then one card per step (one action each: creating a file and pasting into it are two steps), then a summary with an **In a real Fabric app** note linking to Microsoft Learn or rayfin.ai. Every module after the tour ends with two to four questions; each answer links to the step that taught it. Mistakes the lessons are about (a wrong column, a query loop, a mistyped measure) are made on purpose by the learner, then undone; the review lesson is the one place an "agent" drops a ready-made file into the project.

## One project, step by step

There are no start files. A lesson's starting point (its checkpoint) is every earlier step done, from an empty folder. Each step either runs a terminal command (`run`) or carries its exact edit (`edits: [{ file, from, to }]`). The same data drives:

- **Do it for me**: runs the command in the terminal, or makes the edit (Ctrl+Z undoes it, one step at a time);
- the **✓ Done** tick: the command was run (a command the lessons run again, such as `npx rayfin up db apply`, counts once it is in the history that many times), or the files contain the result, however the learner typed it;
- `npm run check`: builds every lesson from empty and type-checks the project after every step, against the error count the step expects (`errors`).

Opening a lesson on a project that isn't at that lesson's start offers the playground's version (with Undo). **Reset** takes a lesson back to its start; **Finish the lesson for me** applies all its steps; **Restart the playground** (lessons drawer and start screen) empties the project and clears progress. All offer Undo.

The playground opens on a start screen with the chapters and one main button, which follows the chapter picked (Start or Continue); a link to a single step skips it, and clicking the brand or the **Playground** tab in the top bar shows it again.

When a step card opens, its spot in the code is marked in pink and its file opens; **Show me in the code** selects it. A step can also point at a part of the playground (`point`), which gets a pink outline that blinks three times; a step that points at a tab of the bottom panel opens that tab.

## Adding a lesson

1. Add its entry to `src/lesson-list.mjs`: `goal`, `builds`, `pbi`, `idea`, `steps` (a `run` or `edits` for every step that changes the project), `summary`, `fabric`. Put long code in `src/course-code.mjs`. Mark glossary words with `[[term]]`.
2. Put its id in a module in `src/course.mjs`. If it teaches something the module's knowledge check should ask, add or change a question there.
3. If it needs new queries, add them to `tools/make-catalog.mjs`, then retake the snapshots.
4. `npm run check`, then click through it in `npm run dev`. Later lessons start from its end, so their edits may need updating.
5. Splitting or adding a step in a lesson people may have started moves their saved positions: point `FROM` in `tools/make-step-moves.mjs` at the last published commit, run it, and raise `STEPS_VERSION` there.
